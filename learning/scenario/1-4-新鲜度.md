## 1 这一步做什么

**新鲜度**＝"这批数据最新到哪一天、算不算新"的档案。它回答的是问数时的第一个实际问题是：*你问的时间段，数据到底覆盖到了没有？* 比如今天 9 月 28 日，有人问"9 月 25 日产量多少"——数据如果只到 8 月 31 日，诚实系统的回答不是硬算一个数，而是"数据截至 8 月 31 日，您问的窗口还没覆盖"。

数据面用一张**登记册**管这件事，三档时效加一档特殊：

| 档位 | 一句话 | 谁会登记 |
|---|---|---|
| realtime 实时 | 秒级/分钟级到账（传感器流） | 实时管道进料时 |
| nearline 近线 | 小时级到账 | 近线管道进料时 |
| offline 离线 | 隔天到账（日批台账） | 1-3 三步契约第三步自动登记 |
| unknown 未登记 | **这张表还没进过料** | 不用登记——查不到就是它 |

本课三件事：①看登记册本体（谁写、怎么写）；②看谁消费它（路由的第二查——"这表进料了吗"）；③**收口 1-1 埋的两个日期**：说明书写"数据截至 2026-08-31"，代码里却写死"2026-09-26"——这一课把这笔账算清。

## 2 调用链：一张登记册，一写一读

```
写方（进料时）：dp2 run_batch_load 第三步 ──▶ ┌ 新鲜度登记册 ──────────────┐
         （或手工 register_freshness）        │ 表名 → (档位, 截至, 管道)   │
                                              │ 没登记过的表 → unknown      │
读方（问数时）：dp6 路由"三查"的第二查 ◀────── └────────────────────────────┘
         "这表的档位和截至是多少？unknown？那拒答"
```

一个先交代的小接线：登记册（FreshnessRegistry）住在 dp2 的 ingest.py 里，但"新鲜度档案"这个数据结构（FreshnessInfo）定义在 dp6 的 freshness.py 里，dp2 借来用（`ingest.py:13` 就是这句 import——import＝程序里"从另一个文件借用现成东西"的语句）——两模块共用同一种"档案格式"，但**写方只有 dp2，读方只有 dp6**，边界清楚。

### 站 1 登记册本体（`ingest.py:37-49` 原文）

```python
class FreshnessRegistry:
    """S1 注册表：{table: FreshnessInfo}；同表多管道取 as_of 最新（DP2 底稿 L52-64）。"""

    def __init__(self):
        self._reg: dict[str, FreshnessInfo] = {}

    def register(self, table: str, tier: str, as_of: datetime, pipeline: str) -> None:
        cur = self._reg.get(table)
        if cur is None or (cur.as_of is None) or (as_of and _as_dt(as_of) > _as_dt(cur.as_of)):
            self._reg[table] = FreshnessInfo(tier=tier, as_of=as_of, pipeline=pipeline)

    def freshness(self, table: str) -> FreshnessInfo:
        return self._reg.get(table, FreshnessInfo(tier="unknown", as_of=None, pipeline=None))
```

三句读法：①册子就是个对照表：表名 → 档案（代码注释里的 `{table: FreshnessInfo}` 就是这个意思的写法，"DP2 底稿 L52-64"＝设计底稿的出处行号）；②登记时**同一张表来两根管道，留 as_of 最新的那份**（as_of，读作"数据截至"——下文沿用英文键名）——实测：先登记 offline/08-31，再登记 realtime/09-28，查出来是 realtime/09-28；③查一张没登记过的表，**不给报错，给 unknown**——"没进过料"本身是一个正式答案，不是异常。

### 站 2 自动登记登记了什么（`ingest.py:77-78`、`ingest.py:93-94`）

1-3 走过的三步契约第三步，登记的三个值原文可查：档位写死 `offline`（写死＝固定填这个值、不随情况变；走批进来的账都是隔天到账）、截至时间＝**写入那一刻的当前时间**（`datetime.now()`）、管道名 `batch-shift-report`。注意：截至时间用的是"现在"，不是"数据真实最后一封账是哪天"——这个含糊马上在站 4 出事。

### 站 3 谁来读：路由的第二查（`freshness.py:79-84` 原文）

```python
    def _freshness(self, md):
        info = self.freshness.freshness(md.sql_table)
        if info.tier == "unknown":
            return None, Refusal("unregistered",
                                 f"表 {md.sql_table} 未登记新鲜度（未进料），暂无可答数据")
        return info, None
```

问数进来，路由先做三查：指标注册了吗（查语义层）→ **表进料了吗（查这张登记册）** → 是不是未来窗。第二查看到 unknown，直接出拒答决定。拒答话术也有合同（`freshness.py:143-146`）：

```python
        if r.kind == "unregistered":
            # 零编数纪律：连"数据截至"都不填
            return r.reason
```

拒答话术那段代码就一句话：拒答理由是"未登记"时，**话术原样返回、一个日期都不加**。看实测（登记册 + 路由接真语义字典；问句里 `granularity`＝粒度，按天/按月/按小时统计的意思）：

```
问"商品量"（它的表 monthly_settlement 没登记）
  → 拒[unregistered] | 话术：表 monthly_settlement 未登记新鲜度（未进料），暂无可答数据
问"产量完成率"（表已登记 offline/2026-08-31，问 2025 年 9 月这个已闭合历史窗）
  → 答 | 档位: offline | 声明截至: 2026-08-31
```

注意拒答话术里**一个数字都没有**——没进料就承认没进料，连"数据截至"都不编。这就是总纲说过的"零编数纪律"在登记册这步的样子。（路由的三查三出口全景在 2-4 展开，这里只看第二查。）

### 站 4 收口：两个日期对不上的账

1-1 埋的问题：fieldforge 说明书（manifest）写"数据截至 **2026-08-31**"，代码里登记的却是"**2026-09-26**"。现在能算清了——**三个 as_of，只有一个是真的**：

| 来源 | as_of | 怎么来的 |
|---|---|---|
| fieldforge manifest | 2026-08-31 | 造数时按数据期末日算的，**真实值** |
| e2e 测试（端到端自动化测试，0-0、1-1 都出现过；`test_tracer_bullet.py:101`） | 2026-09-26 | 人手抄进代码的（测试日 09-27 的"昨天"） |
| 云端 API（`serve/api.py:91`） | 2026-09-26 | 写死的 |

设计文档（PRD §6 供给契约）承诺的是"manifest 的新鲜度自动喂给进料登记"——S1 没接线，人手抄还抄成了另一个数。这不只是标签难看，**实测它能把"该拒答的"放行**：

```
登记 as_of=2026-08-31（真实）：问 2026-09-01..09-20
  → 拒[uncovered] | 话术：数据截至 2026-08-31，未覆盖您问的窗口。请调整查询区间。
登记 as_of=2026-09-26（写死的）：同一问题
  → 答！还声明"数据截至 2026-09-26"
```

数据实际只到 8 月 31 日，但"截至"声明虚标到 9 月 26 日，9 月上旬的窗口被错误放行——答案四件套（0-0 术语表：数字+快照号+质量状态+数据截至）里的"数据截至"这一件在说谎。已按纪律挂进总纲"发现的问题"（**P6**），收官转施工票；修法也明摆着：登记时抄 manifest 的 freshness 段，别自己编。

## 3 服务与中间件卡：unknown 也是一等公民

- **它替我们干了件什么体力活**：把"不知道"变成一个**正式状态**，而不是报错或空值——系统面对"没进料"时的行为是确定的、可测试的、话术统一的。
- **自研还是开源**：约定，自研。三行代码（默认值 unknown + 查不到给默认）。
- **本项目怎么配置使用**：查登记册查不到 → `FreshnessInfo(tier="unknown", as_of=None, pipeline=None)`；路由见 unknown → 固定拒答话术，零编数。
- **市面上同类有哪些**：很多系统用"查无此键就抛错"或返回空值让调用方猜；网站对"查无此页"有个专门的状态码 404（0-0 提过 HTTP＝网页协议）——都是同一思想：**"没找到"要是一个明确的、可辨认的状态，不是含糊的出错**。
- **本项目为什么这么做**：问数场景里"没进料"是常态不是异常（新表上线前的每一天都是 unknown）；把常态建成状态，路由才能对它说固定的诚实话术，自动化测试才能断言它。
- **换场景怎么选**：任何"查不到"会经常发生的领域（资产目录、权限、服务发现），都值得把"查不到"建成一等状态；偶发缺失用报错即可，别过度设计。

## 4 防线对号

- **零编数纪律**：unknown 的拒答连"数据截至"都不填（站 3 原文注释）——宁可少说，不可编造。
- **读写分离**：登记册只有 dp2 写、dp6 读；设计边界规则明文"dp6 不得读湖表数据——只许读 dp2 的档位说明信息"（元数据＝"关于数据的数据"：档位、截至时间这些说明，不是数据本身）。路由判断"能不能答"全程不碰数据。
- **as_of 声明制**：答案四件套的"数据截至"取自登记册——登记错了声明就虚标（P6 反例实测）。声明制的诚实，全凭登记的诚实。

## 6 捣乱实验：谎报截至日，能骗过哪道查、骗不过哪道查

```bash
cd /Users/divh/Downloads/tpa-data-plane
python3 - <<'EOF'
import sys
from datetime import datetime, date
sys.path.insert(0, ".")
from app.data_plane.ingest import FreshnessRegistry
from app.data_plane.freshness import FreshnessRouter
from app.data_plane.semantic import Semantic, StaticYaml

class Clock:
    def today(self): return date(2026, 9, 28)

sem = Semantic(StaticYaml.default())
W  = {"start":"2026-09-01","end":"2026-09-20","granularity":"month"}   # 9 月上旬：真实数据只到 8-31
W2 = {"start":"2026-12-01","end":"2026-12-25","granularity":"month"}   # 12 月：还没发生的日子

reg_true = FreshnessRegistry()
reg_true.register("oil_production_daily", "offline", datetime(2026, 8, 31), "fieldforge-batch")
reg_lie  = FreshnessRegistry()
reg_lie.register("oil_production_daily", "offline", datetime(2026, 9, 26), "fieldforge-batch")  # 谎报+26 天

for name, reg in (("真截至 08-31", reg_true), ("谎报 09-26", reg_lie)):
    r = FreshnessRouter(semantic=sem, freshness=reg, clock=Clock())
    d = r.route(W, "产量完成率")
    print(f"{name} 问9月上旬 →", ("答(声明截至 %s)" % d.declared_as_of) if d.answerable
          else f"拒[{d.refusal.kind}] {r.refusal_text(d)}")
    d2 = r.route(W2, "产量完成率")
    print(f"{name} 问12月   →", ("答" % ()) if d2.answerable else f"拒[{d2.refusal.kind}]（未来窗检查拦的，与 as_of 无关）")
EOF
```

应看到四行，凑成一个完整结论：

- **真截至 08-31** 问 9 月上旬 → 拒[uncovered]（数据截至 2026-08-31，未覆盖您问的窗口）——诚实；
- **谎报 09-26** 问 9 月上旬 → **答了**，还声明"数据截至 2026-09-26"——as_of 的谎能在"已经过去、但晚于真数据"的窗口上得逞（这正是 P6 的危害现场）；
- **两行问 12 月** → 无论有没有谎报，一律拒[future]——**未来窗检查是另一道查（三查的第三查），它看日历不看 as_of**，谎报骗不动它。

这不是 bug，是"声明制"的边界：路由的诚实建立在登记的诚实上（P6 之所以要修，正因为此）。收尾把脚本里标着"谎报+26 天"那一行的 `datetime(2026, 9, 26)` 改回 `datetime(2026, 8, 31)`，**整段重新复制执行**，9 月上旬立刻恢复拒答——防线回来了。
