## 1 这一步做什么

问数系统最堕落的死法不是算错，是**硬答**：数据没到就估一个、粒度对不上就硬凑、用户问未来就编预测。dp6 的存在就是防这个——它站在执行之前，用三道快问决定三种出路：

- **该答** → 指定用哪套数据（实时面还是离线面）并声明"数据截至几点"；
- **暂时答不了** → 明说原因和"什么时候能答"（比如：离线账明天到，明天再问）；
- **永远不该答** → 直说（比如：你问的是还没发生的日子）。

最关键的一条设计纪律：**dp6 不许读湖表数据**（湖＝1-1 说的只加不改的大数据池）。它只看两样东西——登记册（1-4 的新鲜度）和日历。凭什么不读数据也能判断？因为"该不该答"只取决于**元数据**（数据到哪了、口径粒度对不对），跟具体数字无关。这也让它的判断快得像查表。代码证据：整个文件只 import（从别的文件借用，1-3 交代过）了日历和 dp4 的粒度定义（"按月还是按日"这个属性），连湖的门朝哪开都不知道。

另一个反直觉的点：**dp6 里没有 AI**。设计文档明文"路由是确定性代码"——"该不该答"这种判断必须每句都一样、可测试、可审计，交给大模型反而会引入"这次拒下次不拒"的随机诚实。

## 2 调用链：三查三出口

```
结构化查询（2-2 的产物：填好槽位的查询表格）过闸① 后，带着"指标名+时间窗"进闸②
   │
   ▼
三查（每查不过即拒，全程不碰数据）：
   查一 指标注册了吗？      ——查语义层字典（2-2）
   查二 表进料了吗？        ——查新鲜度登记册（1-4）
   查三 问的是不是未来？    ——查日历
   │
   ▼
主干判断（口径粒度 × 时间窗 × 数据档位 → 五个分支）：
   A 月指标×日内窗×不可加   → 拒[granularity] 任何时候都答不了官方口径
   B 日内窗×实时/近线×可加  → 答实时面（强制附口径差异声明）
   B' 日内窗×离线           → 拒[defer] 离线面 T+1，明日此问可答
   C 历史窗已闭合           → 答离线面
   兜底 窗口未闭合          → 拒[uncovered] 请调整查询区间
```

符号先扫盲：判决方括号里的英文（granularity/defer/uncovered…）只是给程序看的记号；B' 读作"B 一撇"＝分支 B 的变体；T+1＝隔天到账；"近线"（nearline）＝小时级到账，比实时慢、比离线快，1-4 三档的中间档；"实时面/离线面"的"面"＝同一批业务的两套数据版本。可加＝各处的数能直接加总（产量吨数可以，"完成率"这种比率不行）。

用人话把五个分支再念一遍：**问还没发生的日子→直说不做预测；急着问今天但只有隔天到账的离线账→今天答不了、明天再来；月度官方指标非要问今天几点→这种指标任何时候都没有"官方的日内数"；数据没定稿但问的是能加总的量→可以答，盖上"临时值"的章；问的是完整过去→放心答离线账。**

### 站 1 三查（`freshness.py:73-92`）

```python
    def _registered(self, metric):
        md = self.semantic.metric_def(metric)
        if md is None:
            return None, Refusal("unregistered", f"指标未在语义层注册：{metric}")
        return md, None

    def _freshness(self, md):
        info = self.freshness.freshness(md.sql_table)
        if info.tier == "unknown":
            return None, Refusal("unregistered",
                                 f"表 {md.sql_table} 未登记新鲜度（未进料），暂无可答数据")
        return info, None

    def _future(self, window) -> Refusal | None:
        """未来窗=起点在今天之后（整窗未发生）；跨今天的窗属 uncovered（兜底分支）。"""
        today = self.clock.today()
        start = window["start"] if isinstance(window, dict) else window.start
        if _as_date(start) > today:
            return Refusal("future", "预测类问题不在数据面处理（不编数）")

```

三查各一句话：查一翻字典（2-2 的指标卡）、查二翻登记册（1-4）、查三看日历。注意查三的细节：**起点在今天之后才算"未来"**；跨着今天的窗（比如问到今天中午）不算未来，走兜底分支判"未覆盖"。

### 站 2 全矩阵实测：七种问法，七种结局

把同一个登记册接到真语义字典上，逐个问（时钟冻结在 2026-09-28，表真实截至 2026-08-31）：

| 问法 | 判决 | 系统给出的原话 |
|---|---|---|
| 问没注册的指标"支持率" | 拒[unregistered] | 指标未在语义层注册：支持率 |
| 问"商品量"（其表未进料） | 拒[unregistered] | 表 monthly_settlement 未登记新鲜度（未进料），暂无可答数据 |
| 问 2026 年 10-11 月（未来） | 拒[future] | 预测类问题不在数据面处理。 |
| 月指标问日内粒度 | 拒[granularity] | ……月度官方口径与所问粒度不符——任何时候都答不了官方口径，您可改问月粒度。 |
| 可加指标问日内×离线 | 拒[defer] | ……离线面 T+1，明日此问可答 |
| 问 2025 年 9 月（历史窗） | **答[offline]** | 声明"数据截至 2026-08-31" |
| 可加指标问今天×实时档 | **答[realtime]** | 强制附带口径声明（站 4） |

七个问法没有一个返回编造的数：四个拒各给原因和出路，两个答各声明用哪套数据截至何时。**拒答本身就是答案的一种**——这句话值得记住。

### 站 3 话术合同：拒答的"四要素"（`freshness.py:139-156`）

```python
    def refusal_text(self, decision: RouteDecision) -> str:
        r = decision.refusal
        if r is None:
            return ""
        if r.kind == "unregistered":
            # 零编数纪律：连"数据截至"都不填
            return r.reason
        as_of = getattr(r, "as_of", "") or ""
        parts = [f"数据截至 {as_of}，未覆盖您问的窗口。"]
        if r.kind == "granularity":
            parts.append(r.reason + "——任何时候都答不了官方口径，您可改问月粒度。")
        elif r.kind == "defer":
            parts.append(r.hint)
        elif r.kind == "future":
            parts.append("预测类问题不在数据面处理。")
        elif r.kind == "uncovered":
            parts.append("您问的窗口晚于数据截至时点，请调整查询区间。")
        return "".join(parts)
```

合同要求拒答话术含**四要素**：数据截至时点、没覆盖你的窗口、为什么、改问路径。唯一例外是"未注册"——连"数据截至"都不填（零编数：没进过料的表，压根没有截至时点可说）。实测每句话术都与合同对得上（站 2 表格右列）。

顺带如实记一个刚测出来的小瑕疵（挂进 0-0 总纲"发现的问题"账本，编号 **P8**；那本账和"收官一起修"的流程 1-2 交代过）：未来窗那句话术开头是"数据截至 ，未覆盖……"——**截至时间是个空**。因为"未来"拒答本来就不涉及截至时点，模板却硬套了这句式。不影响判断正确性，但话术带空格病，收官和 P5 一起修。

## 3 服务与中间件卡（2 张）

### 卡一：Clock——连"今天"都是一个可以替换的零件

- **它替我们干了件什么体力活**：把"今天是几号"从代码里抽出来，变成从外面递进来的一段小程序。生产里递真日历；测试里递一个"永远停在 9 月 28 日"的假日历。
- **自研还是开源**：自研的小设计（行业叫"依赖注入"：依赖的东西从外面塞，不在里面现造）。
- **本项目怎么配置使用**：`FreshnessRouter(…, clock=…)` 构造时递入；本课所有实验把"今天"冻结在 2026-09-28，结果才可复现。
- **市面上同类有哪些**：所有要跟时间打交道的系统都要解决这问题（账务系统的"会计期间"、游戏服务器的时间加速）。
- **为什么值得做**：不冻结时间，"历史窗闭合了吗"这种判断的测试就随日期漂移——今天"绿"（测试通过）的用例下月变红（失败），谁也说不清是代码坏了还是日历走了。
- **换场景怎么选**：凡逻辑里有"今天/过期/宽限期"，都该把时钟当参数递；只有"显示当前时间"这种纯展示逻辑可以直接读钟。

### 卡二：这一闸为什么不用 AI

- **它替我们干了件什么体力活**：用一张**判定表**（粒度×窗型×档位）代替一个"看起来很聪明"的判断者。
- **本项目怎么配置使用**：五分支写死在 `route()` 里；每个分支的拒答话术写死在合同里。
- **市面上同类**：规则引擎、状态机——都是"把判断写成表，不写成直觉"。
- **为什么不请大模型来判断"该不该答"**：①同样的问题今天拒明天答，用户体系立刻崩（诚实必须**每次一样**）；②闸的判决要能写进自动化测试让机器判对错（机判）——AI 的判断没法写死"必须等于几"（这种写死的预期叫断言）；③这一步没有理解成本——输入是结构化的，判据是有限的。**AI 用在听懂人话（上游），规则用在守住底线（这里）**——各干各的。
- **换场景怎么选**：判断的输入结构化、结果要稳定可审计 → 判定表；输入是自由文本、容忍差异 → 才轮到模型。

## 6 捣乱实验：谎报"数据很旧"，和谎报"数据很新"正好对称

```bash
cd /Users/divh/Downloads/tpa-data-plane
python3 - <<'EOF'
import sys
from datetime import datetime, date
sys.path.insert(0, ".")
from app.data_plane.ingest import FreshnessRegistry
from app.data_plane.freshness import FreshnessRouter
from app.data_plane.semantic import Semantic, StaticYaml

class Clock:
    def today(self): return date(2026, 9, 28)

sem = Semantic(StaticYaml.default())
W = {"start":"2025-09-01","end":"2025-09-30","granularity":"month"}

reg_t = FreshnessRegistry()
reg_t.register("oil_production_daily", "offline", datetime(2026, 8, 31), "f")   # 真截至
reg_l = FreshnessRegistry()
reg_l.register("oil_production_daily", "offline", datetime(2025, 1, 1), "f")    # 谎报老了一岁

for name, reg in (("真截至 08-31", reg_t), ("谎报 2025-01-01", reg_l)):
    d = FreshnessRouter(semantic=sem, freshness=reg, clock=Clock()).route(W, "产量完成率")
    print(f"{name} 问 2025-09 →", "答" if d.answerable else f"拒[{d.refusal.kind}]")
EOF
```

应看到：真截至 → 答；谎报老 → **拒[uncovered]**——同一批数、同一个问题，只因为登记册把截至日报旧了，能答的变成了不能答。和 1-4 的 P6（谎报新→错放）正好一对：**登记册报新，闸错放；报旧，闸错拒**。路由的诚实完全建立在登记的诚实上——两课合起来，"登记册必须抄真值"这件事就有了正反两面的证明。
